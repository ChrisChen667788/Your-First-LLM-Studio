## What changed

1. The MLX job bundle now emits an executable `lr_schedule` with computed warmup steps instead of describing scheduler intent in comments.
2. Product target-module names are mapped to MLX module keys and persisted alongside the originally requested names.
3. LoRA scale is emitted as `alpha / rank`, and unsupported packing or training-time checkpoint metrics fail before worker launch.
4. `loadBestCheckpointAtEnd` requires a usable validation split.
5. Runtime attach and evaluation accept a specific checkpoint directory, require MLX adapter weights, constrain the path to the job output, and release a stale loaded alias before switching.
6. Evaluation records the resolved checkpoint and evaluator implementation per score. Loss is explicitly unavailable when the Provider port returns text without logits.
7. ROUGE-L, BLEU-1, exact match, token overlap F1, latency, JSON validity, and the pinned Math-Verify port share a versioned metric registry.

The scheduler contract follows the current MLX-LM configuration entry point and its documented LoRA configuration model: [MLX-LM `lora.py`](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/lora.py) and [MLX-LM LoRA guide](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/LORA.md).
