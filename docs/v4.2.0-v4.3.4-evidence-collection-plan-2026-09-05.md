# v4.2.0-v4.3.4 Evidence Collection Control Plan

Date: 2026-09-06

Implementation audit updated: 2026-09-07. Source: **15/15** repository-owned
mechanisms are implemented. The ten domain collectors now dispatch through
feature-owned adapters, and the eight formerly declarative collectors reject
reference, fixture, and derived read models before receipt submission. This is
not a claim of real workload, reviewer, external, distribution, or production
evidence; those gates remain `HOLD` / `BLOCKED` until live observations are
collected and independently accepted.

## Objective

Turn the v4.0-v4.1 observed-evidence requirements into bounded collection jobs
that operators can queue, workers can safely claim, and distinct reviewers can
accept or reject. This train builds collection mechanics and domain adapter
ports. It does not invent provider traffic, licensed datasets, managed services,
organization identities, external signatures, or production approval.

## Job Lifecycle

1. `queue` validates a collector plan, owned source milestone, durable
   organization/operator identities, subject, and bounded idempotency key.
2. `claim` grants one bounded lease. Recovery after expiry increments a monotonic
   fence token; another active worker and every stale worker are denied.
3. `heartbeat`, `fail`, `retry`, and `cancel` use optimistic job revisions. Retry
   delay is exponential and bounded by the feature plan. Attempt-based fences
   survive lease removal. The 500-job capacity rejects new work without silently
   evicting active jobs or idempotency records. Explicit archival is still TODO.
   Cancellation retains a rejected review in the history.
4. `submit-receipt` reuses the strict v4.0-v4.1 receipt validator. Unknown fields,
   missing metrics, stale timestamps, invalid digests, placeholder identities,
   and failed outcomes do not reach review.
5. `review` requires a reviewer distinct from the collection operator. Accepted
   receipts are content-deduplicated before entering the upstream candidate
   store under its file lock. This is distinct-ID policy, not proof of two
   independently authenticated people. Review and candidate linking can recover
   after an interruption without linking a rejected receipt.
6. The promotion bundle lists only accepted jobs and always retains a separate
   independent acceptance backlog.

## Source And Evidence Boundaries

- Source completion is counted only for implemented mechanisms, not declared
  collection steps. All ten collector dispatchers are now source-complete; a
  collector only forms a candidate from a live observation with every required
  metric. Reference, fixture, and derived read models fail closed.
- Four control milestones can pass local deterministic conformance without a
  provider or managed service.
- Domain milestones require both executable collection code and fresh accepted
  jobs. Provider catalog execution and the eight domain adapters are
  implemented, but every real account, worker, license, managed-service, and
  organization observation still needs collection and review.
- `v4.3.4` also requires the upstream v4.1.4 local gate. Aggregate self-review
  cannot bypass a missing domain receipt.
- Accepted local receipts do not grant external signature, immutable archive,
  distribution, billing, licensing, organization, or production authority.

## Executable Provider Collection

Queue `v4.2.4` / `v4.0.0` with the configured remote target ID (for example
`deepseek-api`) as `subjectId`. `execute` claims a lease, bypasses the cached
model list, and stores a sanitized artifact with advertised IDs, selected and
deprecated aliases, timing, source link and SHA-256. It calls `/models`, not
paid chat completion. Missing configuration, local targets, empty lists and
configured fallbacks cannot become passing receipts. Failed execution enters
bounded retry. Workers submit but never approve their own collection.

The Experiments panel supports queue, explicit execution, retry, cancel,
receipt inspection, accept/reject, gate recording and bundle export. The API
also supports external worker claim/heartbeat/receipt submission. A configured
operator bearer token is kept only in component memory. Field-level validation
rejects unknown properties and numeric coercion before mutation.

For `v4.2.5`, explicit execution runs a fixed 20-item token cohort against the
freshly advertised selected model and a distinct advertised fallback model. It
records output digests, HTTP outcome, latency, primary quality/success rates,
fallback replay count and selected/fallback decision matches. It stores no model
output text and never routes a failed primary into the scorecard. A small token
cohort is transport/conformance evidence, not a product-quality benchmark.
