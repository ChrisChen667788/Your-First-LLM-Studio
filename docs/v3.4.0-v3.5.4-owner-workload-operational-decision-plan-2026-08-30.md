# v3.4.0-v3.5.4 Owner Workload and Operational Decision Plan

Date: 2026-08-30

## Purpose

This 15-version source train turns the v3.2-v3.3 owner execution plan into a
strict workload admission and receipt protocol, then governs the decisions made
from those receipts. It does not execute protected remote mutations and does
not create production authority.

Current source projection is `5 pass`, `8 attention`, `0 unavailable`, and
`2 external-only`. The seven direct workloads remain `0 completed`, `3
admitted`, and `4 blocked` because their real owner-operated evidence is still
absent. Independent external evidence is `0/15`; distribution is `HOLD` and
production is `BLOCKED`.

## Workload protocol

- Seven requests are joined to the existing remediation owner actions.
- Every request carries a stable SHA-256 request digest, idempotency key,
  fencing-token digest, upstream evidence fingerprint, bounded owner review and
  escalation window, and mandatory rollback.
- Requests are `dryRunOnly: true` and `remoteMutationAllowed: false`.
- The candidate receipt validator rejects unknown fields, unknown actions,
  request or idempotency mismatches, invalid/future/stale timestamps, executions
  longer than 24 hours, non-passing outcomes, absent evidence digests, and local
  or fixture identities.
- A valid local receipt is only `valid-candidate`. Detached signature, pinned
  trust anchor, immutable archive, predecessor lineage, and distinct review are
  still verified by the external assurance chain.

## Waiver boundary

Temporary waivers are limited to 24 hours, cannot be renewed, and cannot grant
production authority or bypass signature verification, trust-anchor pinning,
critical security findings, or workspace ACL controls.

## Product and API ownership

- `features/experiments/owner-workload-protocol.ts` owns request and candidate
  receipt contracts.
- `features/experiments/owner-workload-source-signals.ts` owns the 15 source
  projections.
- `features/experiments/owner-workload-admission-application.ts` is the thin
  application boundary for read and receipt-validation actions.
- `GET /api/experiments/owner-workload-admission` reads the v3.4 train.
- `POST /api/experiments/owner-workload-admission` validates a candidate receipt
  without persistence, remote execution, release approval, or production
  transition.
- `GET /api/experiments/operational-decision-governance` reads the v3.5 train.
- Experiments exposes both trains beside v3.0-v3.3 and keeps local, signed, and
  production status visually separate.

## Acceptance

Repository acceptance requires deterministic contracts, strict receipt tests,
all TypeScript partitions, production build, source hygiene, architecture and
durable-state validation, cross-surface route smoke, full HTTP smoke, security
preflight, machine-readable export, and desktop/mobile browser QA.

External acceptance requires separately managed operators, credentials,
services, signatures, trust anchors, immutable archives, observation windows,
and organization authority. Missing external evidence must remain `HOLD` or
`BLOCKED`.
